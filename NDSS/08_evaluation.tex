%-------------------------------------------------------------------------------
\section{Experimental Evaluation}
\label{sec:eval}
%-------------------------------------------------------------------------------

This section runs experiments with the methods and framework above and draws
quantitative conclusions. The internal layered metrics are the lint-coverage
analysis of \S\ref{subsec:coverage} and the end-to-end result snapshot of
\S\ref{subsec:snapshot}. Beyond them, two mutually independent external
validations each check one half of the framework. \S\ref{subsec:lintability-ext}
externally validates rule extraction and lintability determination against the
zlint maintainers' manual gold standard, and \S\ref{subsec:certdetect} externally
validates code generation and synonymy judgment by execution on real
certificates.

\subsection{Experimental Setup}
\label{subsec:setup}

All experiments use GPT-5.4 as the only LLM, and the judges run at temperature~$0$ for reproducibility. We target
RFC~5280 and the CA/Browser Forum Baseline Requirements because they are
the two most authoritative and foundational Web PKI specifications for publicly
trusted TLS certificates. RFC~5280 defines the base X.509 certificate profile that
virtually every downstream rule inherits, and CABF~BR is the baseline every
publicly trusted CA is mandated to meet and itself builds directly on RFC~5280, so
together they bound where compliance linting matters most. Rule extraction was run on CABF~BR~v2.2.6. This was the latest
CABF~BR release when the experiments began.

\subsection{Lint Coverage Analysis}
\label{subsec:coverage}

This subsection measures how many of our lintable rules an existing tool already
implements. We restrict the analysis to zlint---the most widely deployed
certificate linter, integrated into major CA issuance and CT-monitoring
pipelines. The criterion is deliberately strict. A lintable rule counts as
covered only when some cognate zlint lint genuinely implements it, not merely
mentions the same field. We accordingly label each rule full, partial, or none by
whether such a lint implements it fully, partially, or not at all, and count only
full as covered.

In many lints, the description field in metadata is too terse for reliable
semantic matching. We therefore first summarize each lint into a reverse IR in
Stage-0. For every lint we pass three inputs to an offline summarizer
$M_{\mathrm{summ}}$ under a constrained prompt, namely the lint's Go source code,
its Pass/Error test certificates, and its metadata fields description, citation,
and severity. From these we recover the same IR schema our rules use, the core
four-tuple $\langle$subject, obligation, predicate, constraint$\rangle$ plus a
one-sentence code\_summary. Three considerations motivate these inputs. First, the
CheckApplies and Execute branches expose the concrete field and threshold the lint
actually tests, which the metadata description usually omits. Second, the
Pass/Error samples fix the direction of the check, that is, which values it
accepts and which it rejects, together with its applicable scope. Third, casting
the lint into our four-tuple lets rule and lint be compared field by field.
Extracting the full four-tuple, not just the code\_summary sentence, is what lets
Stage-2 compare subject, obligation, predicate, and constraint jointly and reach a
defensible full-versus-partial distinction.

\input{algorithms/alg_coverage}

Given these reverse IRs, Algorithm~\ref{alg:coverage} aligns each rule to zlint in
four further stages that combine deterministic steps with a single controlled
judge. Stage-1 retrieves candidate lints for a rule by provenance. An RFC~5280
rule is matched only against RFC lints whose cited section shares a common prefix
with the rule's section, a test we write \textsc{SectionPrefixMatch}, since RFC
section numbers are stable. Because CABF section numbers drift across versions,
every CABF lint is taken as a candidate for a CABF rule. Stage-2 hands the rule's four-tuple and its candidate set to a
field-level judge $M_{\mathrm{judge}}$, which compares the tuples field by
field and returns the best candidate with a full, partial, or none verdict.
Stage-3 is a deterministic false-positive guard. It maps the subject of the rule
and of the selected lint to a field family such as KeyUsage or SubjectAltName via
$\mathrm{Family}(\cdot)$, and downgrades a full or partial verdict to none whenever
the two resolve to different nonempty families, so a KeyUsage rule is never
credited to a lint that checks SubjectAltName merely because both mention an
extension. Stage-4 aggregates deterministically. A rule is covered if and only if its verdict
is full, and the uncovered remainder forms the code-generation domain $\phi_G$. The LLM is invoked
only at Stage-0 and Stage-2; candidate retrieval, the family guard, and
aggregation are fully deterministic.

Of the 260 lintable rules, zlint fully covers 165 and leaves 95 uncovered under
this procedure, as Table~\ref{tab:coverage} reports. The 95 uncovered rules are
the domain of code generation $\phi_G$. ``full'' counts ``whether one of our rules is fully implemented by some cognate zlint lint''; it does not form a
simple ratio with the total zlint lint count, mainly because one lint can hit
multiple rules.

Under the current codegen domain there are 2 no-template abstentions and, among
the 93 compilable lints after counting the NON\_GENERIC-only extension, 14
generated lints not accepted by the final-shipping synonymy gate. The 35 rules
certified \CodeEqIR{} by certificate-level execution verification are reported
only as collateral IR-level evidence. \CodeEqIR{} is model-independent and
deterministic, yet it does not by itself imply \CodeEqSpec, so the paper-facing
synonymy rate is taken solely from the final emitted code judged against the
source rule.

The first-layer quality signal is G1 conservation, stated as
Theorem~\ref{thm:recall} in \S\ref{subsec:targets}. Under the current snapshot,
conservation holds strictly, instantiating the two appendix
identities~\eqref{eq:cons} and~\eqref{eq:split}:
\[
\begin{array}{c @{\;} c @{\;} c @{\;} c @{\;} c @{\;} c @{\;} c}
  \underset{|\Rkw|}{2080} & = & \underset{|\RN|\ \text{noise}}{513} & + & \underset{|\RL|\ \text{lintable}}{260} & + & \underset{|\RU|\ \text{not lintable}}{1307} \\[3pt]
  \underset{|\RL|}{260} & = & \underset{|\RLcov|\ \text{covered}}{165} & + & \underset{|\RLunc|\ \text{uncovered}}{95}
\end{array}
\]
Both identities hold term by term, so the G1 residual $\Lrec = 0$ and the top two
conservation layers are closed and deterministically recomputable. The first layer
is the three-way recall split of Eq.~\eqref{eq:cons}, and the second is the
covered/uncovered split of the lintable set in Eq.~\eqref{eq:split}. The 260
lintable rules further split by standard source into 175 CABF and 85 RFC~5280, and
the 95 uncovered rules $\RLunc$ are the domain of downstream code generation
$\phi_G$.

\subsection{External Validation of Rule Extraction and Lintability
Determination}
\label{subsec:lintability-ext}

Rule extraction and lintability determination need an independent external
reference. For this we bring in the CABF BR mapping table published by zlint
maintainers~\cite{zlint-mapping-sheet}. This table is manually annotated rule by
rule by zlint experts as to whether a BR requirement can be expressed by a static
lint, and the annotators are unaware of our extractor, IR, and lintability
decider. Each Yes/No label in the table corresponds exactly to our joint output
``extract this rule $+$ decide whether it is lintable'' for the same rule, and
agreement indicates that our rule extraction and lintability determination match
human experts. The table covers two versions, BR~1.4.8~\cite{cabf-br148-md} and
BR~2.0.2~\cite{cabf-br202-md}, compared version-for-version against our
CABF-Server-1.4.8 backend of 422 rules and CABF-Server-2.0.2 backend of 1024
rules, both extracted by the same two-layer pipeline. Table~\ref{tab:extval}
reports the version-for-version agreement.

A small number of sheet rows fall outside our scope, so match coverage is near
87\% on both versions. These rows are title-case or lowercase descriptors such as
``Required if'', ``Deprecated'', or lowercase ``shall'' that RFC~2119 processing
correctly skips, together with, on the BR~2.0.2 sheet, cross-references or chapter
anchors with no matching backend clause. On BR~2.0.2 the matched positive class is
very small, just 12 of 217 matched pairs or 5.5\%, so a naive all-No baseline
already attains 94.5\% agreement. The more meaningful figure is therefore
$\kappa = 0.616$, a substantial agreement on the Landis--Koch
scale~\cite{landis1977measurement}, and the positive-class metrics $P = 0.857$,
$R = 0.50$, and $n = 12$ carry correspondingly wide confidence intervals. BR~1.4.8
has more balanced classes, with 69 of 106 matched pairs positive or 65\%, and
yields $\kappa = 0.823$, an almost-perfect agreement, with positive-class
$F_1 = 0.930$ and zero false positives, a tighter estimate of system quality.

\subsection{Certificate Detection}
\label{subsec:certdetect}

Injecting the 79 final-shipping-unanimous lints into the zlint binary and scanning
certificates checks code generation and synonymy judgment. We count a hit as a
valid finding only when three conditions hold. First, the final zlint code's
semantics have been checked back to the source text. Second, the certificate
yields a non-pass result. Third, an independent structural audit re-derives the
same defect from the DER or openssl. On external corpora we additionally require
that no native zlint lint flags the same certificate, so that existing coverage is
not miscredited to a generated lint. The unit reported in Table~\ref{tab:certfind}
is a certificate-problem instance; duplicated source rows for the same defect are
collapsed.

The testdata column of Table~\ref{tab:certfind} sums to 101 independently
confirmed fixture problem instances. The underlying audit file contains 137
confirmed row-level fixture violations because some defects are represented by
two source rows. Tranco contributes 4 problem instances and CT contributes 1; the
CT instance duplicates one Tranco Root CA, so the external merged total is 4
problem instances, namely 1 Error and 3 Warn. We read severity conservatively.
The AKI and anyPolicy violations are Error-level profile faults whose direct
cryptographic consequence is indirect, while the Root CA CRLDP finding is a
lower, Warn-level advisory.

The corpus first uses zlint's own testdata as a gate rather than an ecosystem
estimate. On 1128 parsable certificates the 79 lints raise 2962 raw
hits. Of these, 137 row-level fixture violations are independently confirmed,
while 2825 are NOCHECK and hence not claimed. To test whether these findings exist only
in hand-constructed testdata, we scan two external corpora. The first is the
TLS-handshake certificate chains of the Tranco Top~1M domains, 47,791 deduplicated
PEMs, and the second is a recent sample of CT logs, 63,327 deduplicated PEMs. The
raw generated-lint hit counts are large, 57,583 on Tranco and 80,021 on CT.

The three confirmation conditions collapse these raw counts sharply. Discarding
every hit on a certificate that some native zlint lint already flags removes the
bulk of them, because most raw matches land on certificates that existing coverage
also rejects, and leaves 1042 candidates on Tranco and 167 on CT. The independent
structural audit then re-derives each surviving defect from the DER and confirms 8
rows on Tranco and 2 rows on CT, marking the remainder NOCHECK and
so not claimed. These rows collapse to the 4 external problem instances in
Table~\ref{tab:certfind}. Each escapes native zlint coverage and
reproduces under an independent audit, so the reading stays conservative and no
finding rests on the generated lint alone.

This external scan checks the second half of the system. The generated lints
generalize beyond hand-built testdata to 111,118 real certificates, where they
surface 4 genuine profile faults that native zlint misses while every claimed
finding survives both a source-text re-check and an independent structural audit.
This indicates that our code generation and synonymy judgment produce checks
faithful to the specification and useful on deployed certificates.
